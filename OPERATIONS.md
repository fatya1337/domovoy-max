# Постоянное размещение и восстановление

## Перед запуском

Нужны сервер с Docker Compose, постоянное доменное имя с DNS на этот сервер и входящие TCP 80/443. Имя может предоставить хостинг: покупать отдельный домен необязательно. Для текущего Caddy важно, чтобы имя указывало на сервер, а порты были доступны; адрес панели управления хостингом не подходит. Бот и miniapp запускаются из compose.max.yaml. Не запускайте второй poller того же токена: при переносе сначала остановите прежний контейнер domovoy-connected-bot на компьютере.

1. Скопируйте исходники и подготовьте `.env.pilot` по `.env.pilot.example` на сервере; права файла `600`.
2. Укажите MAX_BOT_TOKEN, случайный MAX_WEBHOOK_SECRET, ADMIN_IDS, APP_DOMAIN, PUBLIC_ORIGIN. Не включайте MINIAPP_ENABLED до привязки URL организаторами. Учебный диспетчер выключен по умолчанию.
3. Выполните `python3 preflight.py --env .env.pilot`. Скрипт проверяет заполнение, а не DNS или разрешение организаторов.
4. Запустите одной командой:

```sh
docker compose --env-file .env.pilot -f compose.max.yaml up -d --build
```

Сервисы: app (HTTP 8765 внутри Docker), bot (Long Polling), https (Caddy 80/443), backup (копии SQLite). APP_MODE=max не принимает локальные демонстрационные профили. Не публикуйте порт базы или HTTP приложения наружу в обход Caddy.

## После запуска

- `docker compose --env-file .env.pilot -f compose.max.yaml ps` — app должен быть healthy, остальные сервисы запущены.
- Выполните `python3 check_release.py https://ВАШ-ДОМЕН` с другого компьютера: проверяются TLS, health, режим MAX и загрузка HTML, оба JS-файла и CSS. Проверка читает только шесть публичных адресов, не требует токена и не отправляет сообщения. Перенаправления не принимаются: проверяйте конечный адрес. Все строки должны быть PASS. Это не заменяет проверку пользовательских сценариев.
- Проверьте `/start` в боте своим аккаунтом, затем отдельными аккаунтами пройдите сценарий приглашения, заявки, выполнения и подтверждения.
- Проверьте веб- и мобильный MAX после привязки URL. Только после подтверждения включите MINIAPP_ENABLED=1 и пересоздайте сервисы той же командой запуска.
- `docker compose --env-file .env.pilot -f compose.max.yaml logs --tail 30 backup` — должен появиться `Backup ready`.

## Резервные копии

backup.py использует SQLite backup API, а не копирование открытого файла. В каталоге snapshot сохраняются pilot.sqlite3, bot.sqlite3 и manifest.json с SHA256. Для каждой базы выполняется integrity_check. Каталог имеет права 700, файлы — 600. В compose копии создаются каждые 6 часов в отдельном backup-data томе; при неготовности баз повтор через минуту. Автоматического удаления копий пока нет: контролируйте свободное место.

Копии содержат приватные данные приложения. Не включать их в исходники, PDF или общий архив. Отдельный Docker-том защищает от случайной перезаписи рабочей БД, но не от потери сервера. Перенос зашифрованных копий на отдельное хранилище требует выбранного владельцем назначения; он пока не настроен.

Онлайн-копии двух БД снимаются последовательно и НЕ являются общей атомарной транзакцией. Для переноса/восстановления предпочтительна согласованная копия при остановленных app и bot. При восстановлении несогласованной пары могут повторно доставляться уведомления. Не обещаем exactly-once внешнюю доставку MAX.

Создать согласованную копию:

```sh
docker compose --env-file .env.pilot -f compose.max.yaml stop app bot
docker compose --env-file .env.pilot -f compose.max.yaml exec backup python backup.py
docker compose --env-file .env.pilot -f compose.max.yaml start app bot
```

Если резервное копирование завершилось ошибкой, всё равно запустите app и bot обратно и разберите причину. Имя созданной копии будет показано командой. Проверить её:

```sh
docker compose --env-file .env.pilot -f compose.max.yaml exec backup python backup.py --verify /backups/ИМЯ_КОПИИ
```

## Восстановление

Не восстанавливать автоматически поверх работающей БД. Сначала проверить копию; остановить app, bot и backup; сохранить текущие базы и WAL/SHM в отдельный каталог отката; восстановить обе базы из одной согласованной копии с владельцем UID 10001; старые WAL/SHM не оставлять рядом с восстановленными базами. Затем запустить стек и проверить health и контрольную заявку. Процедура требует доступа к конкретному серверу, проверенного пути тома и выбранной копии: универсальная разрушительная команда намеренно не предлагается.

Изолированные тесты восстановления данных из WAL и обнаружения повреждений выполняются командой `python3 -m unittest test_backup -v`; они не затрагивают рабочие данные.

## Проверка Compose на чистых томах

Установите requirements-dev.txt в отдельное виртуальное окружение, затем выполните `python smoke_stack.py` из него. Скрипт создаёт случайный отдельный Compose-проект на основе compose.max.yaml, подменяет только окружение/внешние зависимости тестовыми и проверяет app, сценарии бота на общей базе, Caddy и две резервные копии. Сеть тестового проекта изолирована, обращения к настоящему MAX отсутствуют. Удаляются только временные контейнеры и тома этого случайного проекта.

В этой проверке транспорт MAX заменён локальным вызовом обработчика, Caddy использует HTTP внутри localhost. Она не подтверждает реальные DNS/TLS, мобильный MAX или доступы организаторов — их проверяют отдельно после размещения.

Для SQLite WAL том данных доступен backup-контейнеру с записью: SQLite может создавать служебные WAL/SHM при открытии. Сам backup.py открывает исходную БД в режиме mode=ro и не выполняет изменяющих SQL-запросов. Копии и проверка выполняются в отдельном backup-data томе.

В Compose журналы каждого контейнера ограничены тремя файлами по 10 МБ, чтобы ошибки связи не заполнили небольшой диск. Старые журналы ротируются Docker автоматически. Резервные копии под эту ротацию не попадают.

Чистый Compose smoke также восстанавливает свежую копию в НОВЫЙ временный том и запускает с ним отдельный app. Проверяются сохранённые статусы, связь с аварией, история и транспортная очередь. Это тест восстановления синтетических данных, а не разрешение перезаписывать рабочую базу.
