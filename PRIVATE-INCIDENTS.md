# Приватный учебный диспетчер

Рабочий демонстрационный сценарий: житель сохраняет вымышленное обращение, учебный диспетчер видит очередь, запрашивает уточнение, житель отвечает, диспетчер завершает разбор. Адрес вводится отдельно: членство в подъезде не требуется. История и статусы хранятся в SQLite, никакая внешняя служба не вызывается.

## Проверка в браузере

1. Откройте локальную миниаппу и выберите Анну.
2. Нажмите «Приватные обращения · учебный режим», создайте вымышленное обращение и подтвердите учебный характер.
3. Выберите Илью — учебного диспетчера. Измените статус на «Нужно уточнение», добавьте вопрос.
4. Вернитесь к Анне, откройте историю и добавьте уточнение.
5. Выберите Марию (УК) или Бориса: чужая карточка не отображается.
6. Илья может завершить учебный разбор; закрытая карточка доступна для чтения.

Локальные роли переключаются свободно: это демонстрация разграничения доступа, не защищённая среда для реальных персональных данных.

## Права и эксплуатация

В MAX режим выключен по умолчанию. Для отдельного учебного пилота задайте TRAINING_INCIDENTS_ENABLED=1 и DISPATCHER_IDS с MAX ID уполномоченных учебных диспетчеров, затем пересоздайте контейнеры с новым окружением. ADMIN_IDS не предоставляет диспетчерский доступ. Реальному аккаунту диспетчерские полномочия текущим обновлением не назначались. Существующий бот и публичный пилот сохраняют прежние права.

GET /api/incidents показывает последние 50 карточек автора либо очередь учебного диспетчера. POST /api/incidents создаёт карточку только с training_ack=true. POST /api/incidents/update меняет учебный статус, POST /api/incidents/comment добавляет уточнение. Все операции требуют существующей аутентификации приложения. Сервер проверяет автора/диспетчера, version защищает от конкурентного изменения, request_id предотвращает дублирование при повторе запроса.

Уведомления в MAX, если учебный режим включён, содержат только номер и факт обновления, без адреса и текста обращения. Содержание хранится в incidents/incident_events, не попадает в общие ленты или запрос state. Роль диспетчера видит всю учебную очередь данного экземпляра; региональное разграничение, назначения конкретному сотруднику и политика сроков хранения ещё не реализованы. Это не готовый промышленный контур персональных данных.

Статусы: «Сохранено в учебной системе», «Учебный диспетчер изучает», «Нужно уточнение», «Учебный разбор завершён». Они не означают приём обращения 112 или выезд службы. Прямой набор 112 доступен без создания карточки и верификации.

## Учебный сценарий в боте

При включённом режиме кнопка «Учебные обращения» открывает список. «Новое учебное обращение» проводит через явное подтверждение, вымышленный адрес, описание и проверку перед сохранением. /incident НОМЕР открывает приватную карточку; /incident_reply НОМЕР запрашивает текст уточнения. Учебный диспетчер использует /incident_status НОМЕР review|clarify|closed и затем вводит пояснение. Доступ проверяется тем же модулем, что и в миниаппе. При конфликте версии нужно заново открыть карточку и действие. Повтор события подтверждения не дублирует обращение.

Очередь миниаппы: поиск по номеру, адресу и описанию среди загруженных 50 карточек, фильтры по учебному статусу, общие счётчики, последнее сообщение в карточке. Все просмотры обновляются вручную.
